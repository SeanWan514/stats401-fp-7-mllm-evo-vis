FIRST, A LITTLE CONTEXT

What makes a model
multimodal?

A multimodal large language model (MLLM) combines language with another input type. Here we focus on models that accept images and text: a scanned invoice, a chart, or a photo can become the subject of a question. Open-weight means weights are available; it does not mean every license permits every use.

Our audience is researchers and developers choosing models to test. We connect the repository ecosystem, published benchmark results, and what people discuss when using these models. None is sufficient alone. Popularity is not accuracy, and an issue thread is not a controlled evaluation.

01 / MODEL ECOSYSTEM

18,255 Hugging Face repositories

24,182 API observations → 20,497 unique repositories → 18,255 retained image-and-text candidates. We deduplicate repository IDs, filter conflicting modality/test records, retain missing values, and classify original distributions and derivatives separately.

Dates, families, repository types, licenses and engagement describe the ecosystem. A smaller source-checked set of 57 canonical models supports comparisons; 49 have verified release dates.

02 / COMMUNITY FEEDBACK

21,674 distinct posts & comments

45,047 raw observations → 37,738 distinct source objects → 21,674 retained records from GitHub issues and Hugging Face discussions. We remove duplicates, known maintainers/bots, acknowledgements and off-scope material.

These include questions, problems and experiences—not 21,674 reviews. Rules identify tasks and practical concerns; 1,965 records have task labels. Most attribution is family-level, not exact-model evidence.

Collection, exclusions & label limits ↗
What was acquired, derived, and left uncertain?

Raw API caches, selected source fields, official model cards, acquisition scripts and cleaned tables are in the repository. Benchmark records preserve the OpenVLM baseline and official model-card evidence. The 143,086 numeric benchmark rows are measurements—not additional models. Some first-fetch feedback responses were retained as selected fields; later raw-response samples do not reconstruct every original response.

Family/type and feedback labels are rule-generated and lack human accuracy validation. Source URLs, timestamps, exclusions and uncertainty are retained. Missing scores are never zero; model release dates never come from repository modification dates. Reproduction · Concern counts · Structural checks.

WHAT THE EVIDENCE CAN TELL US

Choice is a tradeoff.
Coverage is part of that choice.

Before deployment, test shortlisted models on your own held-out examples and hardware. Check licensing, failure cases and latency. This atlas helps you decide what to test; it cannot certify a model for your application.

METHODS, LIMITS & DESIGN

Show the work. Keep the uncertainty.

Acquisition & analysis

Hugging Face API discovery uses bounded popularity/recent queries and pagination. Model cards and OpenVLM supply metadata and benchmark evidence. GitHub issues and Hugging Face discussions supply independently identified source objects. Processing retains source/cleaned tables, URLs, timestamps, count ledgers and reproducible scripts. No Reddit corpus or synthetic feedback is claimed.

Task/aspect rules merge synonyms and retain mixed/non-evaluative feedback. Counts are source objects, not sentences or independent users. Exact-model and family attribution stay separate. Downloads, issue counts and sentiment are not performance scores.

Limits & next steps

Repository relevance and family/type classifications are metadata-based. Feedback overrepresents support forums and English/Chinese rule matches; labels have no measured human accuracy. Only a minority identify a task or exact model. Benchmarks differ in protocols; even same-table scores may have incomplete settings. These limits constrain interpretation; they are not evidence of poor models.

Next: independently review labels and attribution, test with target users, collect controlled speed/memory measurements, expand source diversity, and evaluate shortlisted models on application examples. The project-member review and production workflow check are documented above; no independent user study or annotation agreement is claimed.
