Dataset and processing

Actual OpenVLM data, reduced for transparent comparison

The raw snapshot contains model metadata and nested benchmark results from the OpenVLM leaderboard. The interim build preserves the raw JSON, then extracts a compact model table with release date, provider, open-weight status, reported parameter count, language backbone, vision encoder, and six well-covered overall benchmark scores.

Cleaning standardizes dates, parses reported parameter counts into billions, repairs a small set of recurring organization labels, groups related language and vision backbones, and leaves absent values as not reported. Scores from different benchmarks are never averaged into a synthetic ranking because their scales and tasks differ.

  • Raw: 285 model records and 6,584 benchmark result blocks.
  • Processed: one row per model plus six comparable score fields used by the prototype.
  • Coverage: 229 parameter counts, 224 language backbones, and 219 vision encoders.
  • Release-date window: April 2023 to February 2026.
  • Audit flag: the file timestamp is September 17, 2025, but one record is dated February 13, 2026; that record needs source verification before final analysis.

Source: OpenVLM Leaderboard. “Open-weight” follows the dataset’s OpenSource flag; it does not guarantee an open license, training code, or training data.

Evaluation plan

Test whether the dashboard improves model-choice reasoning

We will conduct task-based usability sessions with 6–10 students or technically interested users. Each participant will complete three scenarios: shortlist an open-weight model under a parameter budget, compare two architecture branches, and explain one provider–family lineage. We will record task completion, time, errors, filter paths, and whether the final answer cites evidence from more than one view.

Afterward, participants will rate clarity, confidence, perceived usefulness, and trust in the missing-data treatment on five-point scales, followed by two open questions about confusion and desired information. We will also run a checklist-based design review for legibility, color/shape redundancy, keyboard access, tooltip completeness, benchmark comparability, and mobile layout.

Success criteria: at least 80% correct task completion, median confidence of 4/5 or higher, no systematic benchmark-scale confusion, and actionable qualitative feedback rather than only aesthetic preference.

Data extension plan

New-model discovery and public feedback

Model updates

A reproducible script queries the Hugging Face API for recently updated image-to-text models and writes a review queue. Candidates are not merged automatically: the team will verify release date, open-weight status, provider, parameters, architecture, and benchmark protocol first.

Comments and sentiment

Public or consented comments can add a reception layer, but sentiment is not evidence of model quality. The prototype scorer keeps source, URL, date, and model fields so platform bias, duplicate text, language coverage, and temporal drift can be audited. A manually labelled sample is required before interpretation.

Why this is enough data

The existing file already contains more than 140,000 numeric measurements. Comments should therefore answer a distinct question—how users discuss reliability, speed, or failure modes—not merely inflate the row count.

What we will add verbally

Interpretation prompts for the in-class check-in

  1. Identify one model whose benchmark score is unusually high for its reported size, while avoiding a causal “efficiency” claim.
  2. Point out one language or vision backbone that appears across multiple providers and explain why linked highlighting would help.
  3. Explain why missing parameter or architecture fields remain visible rather than being guessed.
  4. Ask the teaching team whether the four coordinated temporal views count as distinct interim visualizations and whether the provider lineage map meets the final complex-idiom requirement.
